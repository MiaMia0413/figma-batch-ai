# 产品与工程行为手册

这个项目仍在开发阶段，手册的目标不是限制探索，而是防止产品方向、工程边界和通用性在迭代中跑偏。每次修改产品行为、工具 schema、提示词或匹配逻辑前，都先快速对照这份手册。

## 规则等级

- **硬约束**：必须遵守。除非用户明确要求调整产品方向，否则不要突破。
- **默认原则**：正常功能路径应该遵守；如果为了验证原型需要临时例外，要在代码、文档或提交说明中写清楚原因。
- **可实验例外**：开发阶段允许探索，但不能悄悄变成默认产品行为。

## 产品定位

- **硬约束**：第一交互方式是自然语言编辑已有设计稿。用户不应该被迫先精确选中目标图层。
- **硬约束**：选中图层是第二交互方式，用于缩小范围，而不是使用产品的必要前置步骤。
- **硬约束**：不要把示例、测试用例或某个用户文件中的业务词写进产品逻辑、prompt 或匹配规则。
- **默认原则**：产品主要编辑已有 Figma 文件，不以从零生成完整 UI 为默认能力。
- **默认原则**：用户意图应该综合图层名称、可见文本、层级关系、几何信息和已有图层属性来判断。
- **默认原则**：当用户选中 Frame、Group、Component 或 Instance 时，工具应该向内检索子图层，并结合容器上下文判断可修改对象。
- **可实验例外**：可以探索生成新模块、新组件或新页面，但需要作为显式实验能力，不要混入普通编辑路径。

## 匹配规则

- **硬约束**：target 必须来自用户原话或用户明确确认的选择，不能由模型用 inspection 中看到的其他标签替换。
- **硬约束**：精准匹配失败时，不能静默降级成宽泛匹配并直接修改。
- **硬约束**：匹配逻辑必须保持通用，不绑定某个业务、活动、文件或公司语境。
- **默认原则**：优先使用完整短语和强结构匹配，再考虑宽泛 token 匹配。
- **默认原则**：页面级修改类操作需要 target；只有用户明确要求修改整页时，才允许不带 target。
- **默认原则**：如果目标不存在、过宽或有歧义，应该追问、预览或拒绝，而不是猜测。
- **默认原则**：对按钮、标签、选项卡、卡片、列表项、菜单项、导航项、表单控件等组状 UI 目标，应该把匹配到的容器作为上下文，并编辑最相关的子图层。
- **可实验例外**：可以做语义召回、近义词、视觉相似性等探索，但实验结果进入修改命令前仍需要安全校验。

## 编辑安全

- **硬约束**：修改安全必须由确定性代码兜底，不能只依赖模型自觉。
- **硬约束**：会修改异常多图层的操作必须被拒绝、预览或要求用户缩小范围。
- **硬约束**：执行结果要能说明 scope、target 和实际修改数量。
- **默认原则**：高影响修改在正式功能路径中需要 UI 确认。
- **默认原则**：页面级编辑要比选区级编辑有更严格的安全阈值。
- **默认原则**：用户要求修改背景色或填充色时，不要顺手修改文字颜色，除非用户明确要求改文字颜色。
- **默认原则**：优先做小范围、可撤销的修改，避免扫射式修改。
- **可实验例外**：开发调试时可以用显式 debug 开关绕过确认或放宽阈值，但不能默认开启，也不能进入面向用户的普通路径。

## Prompt 与工具设计

- **硬约束**：Prompt 不要写入某个业务场景里的具体词，尤其不能把测试用例变成长期规则。
- **硬约束**：工具 schema 和主线程命令必须保持 allowlist 模式，模型不能执行任意 Figma 操作。
- **默认原则**：Prompt 描述长期稳定的行为原则，而不是补丁式修某一次模型错误。
- **默认原则**：工具 schema 应该让正确行为更容易发生，必要时使用明确字段，例如 `target`、`scope` 和意图标记。
- **默认原则**：用户请求应先进入统一的 Edit Plan，再走 Preview 和 Apply。不要把新的句式规则散落在工具循环里。
- **默认原则**：新增自然语言能力时，先在统一意图层抽取 `intent`、`target`、`scope`、数量、位置、布局、属性和值等通用槽位，再映射到具体工具；不要为单一功能长期堆独立解析分支。
- **默认原则**：UI 工具循环在命令进入 Figma 主线程前执行关键约束校验；主线程在真正修改节点前再次校验。
- **默认原则**：模型可以负责理解、规划和选择工具，但修改边界和安全策略放在代码里。
- **可实验例外**：可以临时增加诊断工具、调试输出或实验 schema，但要避免污染稳定工具集。

## 工程原则

- **硬约束**：保持 `src/main/` 和 `src/ui/` 职责分离：
  - `src/ui/`：聊天 UI、模型请求、工具循环、用户确认。
  - `src/main/`：Figma API 访问、命令允许列表、参数校验、节点修改。
- **硬约束**：`src/shared/` 只能包含不依赖 DOM、网络和 Figma Plugin API 的纯逻辑。
- **硬约束**：工具 schema、确认要求和预览策略统一定义在 `src/shared/tool-registry.js`，不得在 UI 与主线程重复维护。
- **硬约束**：修改会影响 Figma 加载行为的源码后，必须用 `npm run build` 更新 `dist/` 生成文件。
- **硬约束**：修改源码、文档、脚本、manifest 或生成产物后，运行 `npm run verify`。
- **硬约束**：批量修改必须支持单节点失败隔离；取消和安全错误不得被当作普通跳过项吞掉。
- **硬约束**：每个成功且实际写入画布的工具命令必须提交独立撤销边界；只读命令和零修改结果不得创建空撤销步骤。
- **默认原则**：匹配和校验逻辑优先写成小模块和纯辅助函数，方便测试与复用。
- **默认原则**：目标范围、节点遍历、显式 nodeIds 和语义匹配分别放在 `selection/` 与 `targets/`，具体工具只负责规划和应用修改。
- **默认原则**：主线程命令保持串行；长遍历或批量写入要提供协作式取消检查点。
- **默认原则**：工具保持通用，不把服务商、公司、文件、活动或业务规则写进核心工具。
- **默认原则**：新增能力优先沿用现有命令注册、工具 schema、构建和检查机制。
- **可实验例外**：可以快速做原型文件或临时验证代码，但进入主路径前要整理成可维护结构。

## Review Checklist

- 这次改动是否仍然保持“自然语言编辑当前设计稿”为第一交互方式？
- 选区是否仍然只是可选的范围限制，而不是前置要求？
- 这个改动有没有可能误改大量无关图层？
- target 是否来自用户意图，而不是来自示例、测试词或模型猜测？
- 模糊匹配是否通过追问、预览、拒绝或安全阈值处理？
- 这条规则是硬约束、默认原则，还是实验例外？是否写清楚了？
- 这个能力是否足够通用，能适配不同团队和不同设计文件？
- 是否新增或更新了对应的自动化测试？
- 工具元数据、主线程 handler 和预览策略是否一致？
- 用户停止后是否会阻止后续选区变化和画布写入？
- 实际画布写入是否提交了独立撤销点，且只读或零修改结果没有污染撤销历史？
- 源码和 `dist/` 生成文件是否同步？
